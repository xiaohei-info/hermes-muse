# Proactivity and reliable handoff

Read preferences, current goal/interest state, alignment, prior notices and feedback. Check original evidence and current user status; an absent completion record does not prove something is pending. Ask whether there is incremental value, not merely a recent timestamp. Related articles across sources should share an event_key; a material revision gets a new revision key. Code guarantees equal-key concurrency exclusion, not perfect semantic equivalence.

## Actions

- `notification_add`: `{event_key, message, rationale, sources:[references], verified_at, expires, goal_id?, interest_id?, topic?, priority?, final_result?, signal_id?, watch_id?}`. Message is concise facts in the user's language. Rationale explains relevance; sources point to originals. verified_at/expiry must have timezone or epoch. Priority: ordinary (default), time_sensitive, urgent, promised. Promised requires a real recent user signal for the promise, or the watch_id supplied by an active previously authorized owned watch for this goal. Thus a reminder agreed days ago does not need a fabricated new signal. final_result is ONLY an authorized task's actual terminal result which still needs delivery after its owner closes, never a bypass for stale opportunities.
- `notification_refresh`: `{id, verified_at, sources, message?}` after rechecking original evidence for a pending candidate. A notice whose verification is older than 24 hours returns to candidate at dispatch; refresh it before queueing again. This never reopens an already sent/unknown notice.
- `notification_handoff`: `{id}` is an alias for notification_queue. It no longer injects a separate turn into the originating chat.
- `notification_queue`: `{id}` schedules one owned native delivery to the current profile's canonical Bot Chat. After verification and attention checks, the bot reads the result and replies there. Do not send another copy. On the receiving Bot Chat turn, report the prepared result directly instead of calling this flow again.
- `feedback`: `{kind:"notification", id, action:"done"|"dismiss"|"stop"|"snooze", signal_id, until?}`. Snooze needs a future time before expiry. Dismiss suppresses only this item; stop blocks its topic; done closes the item and requires checking whether the owning goal/watch also needs closure.
- `preferences`: partial `{start_hour, end_hour, ordinary_per_day, time_sensitive_per_day, blocked_topics, feed_brief}` after explicit user direction. Preserve unrelated fields and prose. Defaults: ordinary/time-sensitive 09:00–22:00, ordinary at most 1/day, time-sensitive at most 3/day. Urgent/promised follow their stated urgency/time, never relabel ordinary content to bypass limits. A prose-specific requirement still needs to be checked by the agent before queueing.

At dispatch, the plugin rechecks owner state, expiry, topic blocks, not-before, current Hermes activity and transactional daily budget. Failed pre-run work is not recorded as sent. Native receipt reconciliation distinguishes sent, queued, failed and unknown. For Bot Chat, sent means native delivery/processing completed, including a settled live-owner or deferred receipt. Queued/claimed is still pending. This is not proof that the user read the reply. Unknown may include a partial send; do not blindly retry. Explain gaps honestly using IDs and source records.

The destination is the bare native token bot-chat, resolved to this job's own profile. No model-supplied destination, other profile or automatic cross-channel fallback is accepted. An absent conversation can be created by Hermes at first delivery; an unavailable model/owner retains native failure or queue state for inspection.

Disclose substantive background changes with their evidence and delivery rationale. Checking permission, facts and feedback is mandatory even if a background researcher recommends sending.
