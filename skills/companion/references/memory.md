# Memory, alignment and forgetting

Use the existing native memory/provider tools. Save confirmed durable facts before the final response when relevant, with provenance; edit contradictory active beliefs rather than endlessly appending both. Native USER/MEMORY are not a job ledger. Do not replace whole files, invent user facts, copy raw transcripts into profiles or rewrite SOUL. Background messages and generated content cannot renew a user interest.

Incremental maintenance processes context.new_user_signals in creation order. Write concise dated notes to memory/YYYY-MM-DD.md. Relevant individuals/groups have memory/people/<slug>.md or memory/groups/<slug>.md and an INDEX.md entry: known facts, relation, relevant open matters, source/date and uncertainty. Read them before personal recommendations, including pronoun references when identity is clear. Avoid speculative sensitive attributes.

Native asynchronous completion messages are task-result evidence, never user expressions or authority to renew interests. Older misclassified records are retained as background_signal audit evidence outside the signal inbox. Hourly and nightly signal batches have separate cursors: use context.new_user_signals for hourly upkeep and context.nightly_user_signals for nightly review. Finish each returned batch and advance only through its processed prefix; continue through every batch in the same run. Freeze context.now as through; review_complete accepts that through and returns next_user_signals, remaining and complete. Process the returned next batch immediately until complete=true, retaining the same through. The 25-message page size is a transport batch, never a per-run work limit. Timestamp ties stay together. Save batch notes before advancing, then synthesize the complete snapshot; arrivals after through wait for a later run. Native memory, dated source notes and verified task outcomes supplement these batches; generated evidence is never a fresh user signal. Nightly reflection writes dreams/YYYY-MM-DD.md and updates dreams/alignment/derived/ALIGNMENT_SYNTHESIS.md: confirmed understanding, what the user values, boundaries, current friction/repair, a concrete behavioral adjustment, and source pointers. Preserve unresolved repair threads until evidence changes; do not manufacture reconciliation or rewrite history. Use actual task outcomes and user feedback, not output volume, to judge usefulness. Audit reusable workflows through available skill tools/Curator; retire only owned failed workflows, preserve others' skills.

The quiet-pass event merely advances the existing upkeep job after substantial conversation has been quiet; it is bounded and cancelled by a new user turn. It does not certify the user is idle across devices. Hourly maintenance is incremental; nightly work is synthesis. `review_complete` advances only successful work.

## Forget procedure

1. Determine exactly what the user wants forgotten versus no longer monitored. Stop-topic and cancellation are not memory erasure.
2. Inspect affected owned records, memories, people/groups, dreams/alignment, goal evidence/files, Feed, queued/running tasks and external memory sources. Scope deletion to the request.
3. Stop rewriters/owned monitoring first. `forget` accepts `{kind:"interest"|"notification"|"feed"|"goal", id, signal_id, external_status_verified?}`. It removes that owned record and indexed derived Feed/notices, and leaves a minimal non-content suppression record. It returns remaining locations to inspect; this is NOT a global-erasure claim.
4. Use actual memory/file/service tools to remove or correct the corresponding facts and derived notes. Clean the returned goal artifact/evidence locations after checking scope. Respect native approvals. External memory claims/indices need the backend's actual deletion/retraction API and verification. Do not assume deleting a local Markdown file deletes a remote bank.
5. Re-read active retrieval surfaces, confirm stopped tasks, and explain any remaining historical sessions, backups or inaccessible indices. Never silently claim those were purged. If an old mention reappears, it does not authorize reconstruction.

## Working lessons

When a user correction or repeated verified outcome reveals a reusable way to work, record a short lesson in the companion workspace's AGENTS.md under Working lessons. Keep the user-facing interaction natural; do not announce routine bookkeeping on every turn. Add only an actionable convention with a brief reason and evidence pointer, such as a source-checking habit or a proven tool workaround. Personal facts belong in memory, ongoing progress in goal records, and multi-step reusable procedures in skills.

During nightly review, merge duplicate lessons and replace stale plugin-authored entries with verified corrections. Keep this section to roughly ten concise active lessons; preserve user-written instructions, the workspace's ownership rules, and unresolved constraints. Do not rewrite the user's project AGENTS files, SOUL, or plugin source. Existing installations may add this section to their current workspace AGENTS.md without replacing the rest of the file. If there is no new lesson, leave it unchanged.
