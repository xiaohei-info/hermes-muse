# Goals and interest lifecycle

Read context before acting. A clear user commitment or concrete plan permits a goal even when phrased as conversation rather than “create a goal”; a passing mention or speculative wish permits only a temporary interest. Preserve the user's actual scope and outcome, and check for an existing goal before creating another. Never assume a suggestion was accepted. An existing external task/goal stays authoritative: record its reference, use its tools to verify changes, and do not invent a competing completion state.

## Actions

- `goal_create`: `{id?, title, description, completion_criteria, signal_id, parent_id?, deadline?, external_ref?}`. IDs use ASCII letters/numbers/hyphens/underscores. One level of subgoals. The record owns a source session, current status and a research review date. Deadlines are ISO timestamps WITH timezone. User explicitly stated constraints belong in description/criteria; preserve financial/health/relationship judgment boundaries.
- `goal_update`: `{id, progress?, status?, signal_id?, research_review_at?, external_status_verified?, outcome_evidence?}`. Progress must point to evidence/artifacts. Status is active/completed/cancelled. Cancellation, reopening and review extensions need a recent real user signal; an external authoritative cancellation may instead use verified outcome_evidence plus external_status_verified. Completion may instead use outcome_evidence `{sources:[references], verified_at, summary}` from a current verified outcome that satisfies the existing accepted completion criteria. A pending user decision cannot be invented: if the criteria require user confirmation, obtain it. Explain what was completed and keep final delivery open. This allows cross-day completion without manufacturing a fresh user message. Before external_ref completion verify/update the external source. Closing a parent cancels remaining active children and pauses owned watches. Reopen does not resume them automatically.
- `interest_record`: `{id?, title, signal_id, expires?, rationale?}`. Defaults to 14 days from the actual user signal; earlier events shorten it. Reuse the same ID for the same topic. A later mention may renew it; rereading the old mention cannot. Stable enduring preferences belong in native memory/preferences, not an endless chain of temporary renewals.
- `idea_add`: `{goal_id?, title, rationale, sources?, expires?}`. Research can suggest an Idea for a currently eligible goal or from verified personal context; independent Ideas require original source/context references. Use an earlier expiry for dated opportunities. It expires after 14 days, is deduplicated and is not a task. Rank fit, feasibility and novelty; acceptance requires user feedback and a new explicit goal/task if execution is requested.
- `watch_create`: `{goal_id, signal_id, schedule, prompt, stop_condition, expires?}`. Only for explicitly agreed monitoring/reminders. Native schedule syntax (cron expression or future timestamp); include evidence source, notification condition and terminal condition. Do not create one watch per temporary interest. When the user gives an end date, set expires to that timezone-aware timestamp; the script gate stops it even if no model can run. Record/verify the returned native ID.
- `watch_stop`: `{job_id}` pauses only owned watches. Use when the condition is resolved, scope is revoked, or the user cancels.
- `feedback`: `{kind:"interest", id, action:"accept"|"done"|"dismiss"|"stop", signal_id}`. Accepting an Idea alone does not execute it.

Undated formal goals request an internal research review after 30 days. Do not mark them completed because they went quiet. Present a review only when useful; pause additional unsolicited research, preserve explicit recurring subscriptions, and never renew based on your own activity. Check expiry on EVERY read/send, not just the nightly pass.

When finishing: update the authoritative outcome, write a short progress/evidence note, stop owned future work, preserve an explicitly marked final result for delivery, and reconcile any already running work. A cancelled watch cannot undo external actions already submitted.

Use the communication procedure when bringing back progress or a result. Complete useful work within the accepted scope before asking a generic next-step question. Mention a past conversation only with evidence; never turn the framing of a message into a new commitment.

## Accepting and changing a watch

Use the communication procedure's task-taking judgment. Establish from the current request and existing context what outcome matters, which sources are relevant, the check cadence, what qualifies for notification, how genuine failures are handled and the actual stopping condition. Resolve routine details yourself; clarify only a material missing choice. Do not promise a threshold, source coverage or recovery action that has not been implemented.

Persist these rules in the watch prompt and relevant goal progress/evidence, rather than only in the chat reply. Explicit report subscriptions keep their promised reporting cadence; change-detection watches can check frequently and notify only for valuable changes. A single watch's condition is not a global preference change. Keep original source/account scope, timezone, active window, expiry, quiet-hour preferences and stop rules unless the user changed them. Adding sources also calls for comparable units, timeframes and conditions where relevant; user intent and actual source evidence decide the details.

For a frequency or scope change, first use muse_manage status plus native Cron inspection to locate the actual job. watch_create always creates a new watch; it is not an update API. Use Hermes's existing Cron update action for the same job ID. Preserve its plugin ownership marker, generated execution/delivery instructions, Skill, script, workdir, route, model, pause state and unrelated user settings. Read back the job to verify the new schedule/prompt and that the original task remains the single intended watch. Do not hand-edit jobs.json/install.json/state.db or create a replacement merely to make the confirmation easy. Lifecycle changes must also respect the goal and recorded watch expiry; changing prompt text alone cannot extend the script's expiry gate.

If independent research is already running, use the host's supported steering mechanism when available and confirm the steering result. Otherwise record the revised request, reconcile the returning result and do the remaining authorized work; do not claim a running child has been redirected or start duplicate work. Explain what is ready and what still depends on an unfinished step.
